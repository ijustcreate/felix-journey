Experience problem

The system never has perfect evidence.

GPS may be accurate enough to approach a location but not prove arrival. A camera may see the right color and wrong shape. A compass may oscillate. Network sync may disappear after the child has already found the thing.

Quest Compass exposes the state of each subsystem rather than flattening uncertainty into one smug green checkmark. GPS and camera permissions are requested only after a relevant action. The camera progresses through searching, signal found, holding steady and locked. A wrong glyph cannot satisfy the objective. Local quests remain useful when cloud services are unavailable.

UX evaluation framework

Affordance → evidence → feedback → consequence → recovery.

MomentQuality questionFailure pattern
PermissionDoes the request arrive when the user understands why?Camera/GPS prompt on launch with no context.

FeedbackCan the child improve the signal?A generic failure with no light, stability or direction cue.

Implementation evidence

The scanner makes uncertainty visible.

The public camera module performs local canvas analysis for color and shape, corrects against estimated scene lighting, scores candidate confidence, smooths output, requires stable frames, and then requires a timed hold before confirming. The interface can therefore distinguish “something is visible” from “the requested glyph is stable enough to count.”

Documented limitations remain visible: browser compass behavior varies, GPS is not room-precise, local accounts are convenience profiles rather than secure identity, and the heuristic scanner is sensitive to lighting, blur, shadows, distance and marker geometry.
